## 1. 概述

在保留现有 LangGraph 业务流程的前提下，让模型在节点允许的范围内直接选择平台工具并生成业务参数。模型输出仅是候选调用。Harness 在执行前验证工具名、参数 Schema 和当前调用权限，再交给工具注册器执行；Node 继续负责任务阶段、前置检查、人工确认、结果处理与后续流转。

核心调用链：

```text
用户请求 → 意图路由 → 业务 Node 确定当前阶段和可用工具
                     → 模型生成候选 tool_call(name, arguments)
                     → Harness 校验名称、Schema、调用策略
                     → 平台工具执行 → 结果写入 State → Node 决定下一阶段
```

## 2. 背景与现状

当前实现的可选 LLM 主要输出 `IntentResult`（意图、置信度和实体）；置信度低或输出异常时回退规则路由。`graph.py` 根据意图进入固定业务节点。节点从路由实体、会话 State 和代码常量组装参数，再通过 `ToolBatch.call` 调用平台工具。例如资产发现节点以用户消息作为 `search_data_assets.query`，并在代码中给定 `limit=5`；查询准备节点按固定顺序调用 `validate_sql`、`parse_sql`、`batch_check_permission`，满足条件才进入执行节点。

因此，**本项目当前没有让 LLM 自由生成平台工具名与调用参数**。现有 `ToolRegistry` 检查工具是否注册并负责调用与审计，但没有在统一入口对模型候选参数执行完整 Schema 验证。`api_contracts.py` 中已有部分 HTTP 请求模型，可作为设计参考；其覆盖范围和字段定义需要与面向模型的工具契约逐一核对，不能直接视为统一 Harness 已存在。

固定流程降低了调用风险，但对需要从自然语言中选择查询工具、组合过滤条件或补全业务参数的场景，节点代码需要不断增加分支。优化目标是让模型承担受限的工具选择与业务参数生成，同时保留节点的流程控制和程序校验。

## 3. 目标与范围

### 3.1 目标

1. 模型只在当前 Node 提供的候选工具中选择工具，并生成业务参数；Node 能继续决定执行顺序与下一步。
2. 每次模型候选调用在进入平台适配器前，都经过 Harness 的工具名和参数 Schema 校验。
3. 用户身份、会话、任务 ID、授权范围及确认状态由服务端注入，模型不能生成或覆盖。
4. 缺参、歧义、非法参数和工具异常有明确的用户反馈、有限重试及审计记录。
5. 现有规则路由、固定节点流程、权限检查、只读 SQL 限制及人工确认行为保持可用。

### 3.2 首期范围

先覆盖只读、低风险的资产发现和元数据查询：`search_data_assets`、`get_table_metadata`、`get_column_metadata`、`search_metrics`、`get_metric_definition`。节点可根据本阶段需要收窄候选集合；上列是首期工具全集，不表示每个阶段全部开放。权限查询、SQL 执行、权限工单、DAG 提交/触发/回填等流程继续由现有节点控制，后续分期逐步接入候选调用机制。

### 3.3 本期不包含

- 让模型自主创建、修改或跳过 LangGraph 节点与边。
- 将平台的全部工具一次性暴露给模型，或根据模型自报权限放行调用。
- 模型自行决定执行 SQL、创建权限工单或提交/触发 DAG。
- 以 Prompt 中的约束代替服务端校验、权限检查或人工确认。

## 4. 职责边界

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| LLM | 基于当前任务上下文，在可见工具中提出 `name` 与业务 `arguments`；无法判断时要求澄清 | 执行工具、声明已获授权、写入可信身份字段 |
| Node | 确定任务阶段、候选工具和调用次数；执行前置条件；消费工具结果、更新 State、决定流转和确认时机 | 将模型参数视为已校验的事实 |
| Harness | 接收候选调用；校验工具名、参数 Schema、服务端字段和阶段策略；统一执行、限额、错误映射与审计 | 替代 Node 决定完整业务流程 |
| 平台适配器 | 按真实用户身份执行平台能力并返回事实；保持平台侧授权 | 信任模型生成的用户身份或权限 |

`ToolRegistry` 可演进为 Harness 的执行底座，也可由 Harness 包装；实现时须保证所有**模型候选调用**只能经过同一验证入口。节点发起的固定工具调用可复用该入口，避免两套契约逐渐不一致。

## 5. 目标流程与交互

### 5.1 正常流程

1. `prepare -> route` 保留。Node 根据当前意图、State 和上一步工具结果，决定当前阶段及该阶段可用工具。
2. Harness 将工具说明和参数 Schema 提供给模型。模型返回一个结构化候选调用，或返回 `needs_clarification`。首期每轮最多一个候选调用。
3. Harness 检查名称属于该阶段允许集合，并以对应 Schema 严格验证 `arguments`：类型、必填项、枚举、范围、嵌套字段及额外字段。
4. Harness 从服务端上下文注入可信字段，检查资源范围、调用预算和当前阶段策略。通过后才调用 `ToolRegistry` 与平台适配器。
5. 调用结果和调用记录写入 State。Node 解释结果、继续下一阶段或结束任务。工具返回内容仅作为数据，不得当作新的流程指令。

示例：用户问“找与订单退款有关的表”。资产发现 Node 开放 `search_data_assets`；模型输出 `{"name":"search_data_assets","arguments":{"query":"订单退款相关数据表","limit":5}}`。Harness 验证后执行；Node 根据候选结果决定是否继续读取表元数据，并最终生成带有平台事实的回答。

### 5.2 校验失败与澄清

| 情况 | 处理 |
| --- | --- |
| 工具名不存在或不在本阶段允许集合 | 不执行；记录拒绝原因；最多允许一次受限纠错重试，仍失败则结束并提示无法完成 |
| JSON 不可解析、缺少必填字段、类型/枚举/范围错误、包含额外字段 | 不执行；返回结构化字段错误供模型纠错；重试次数耗尽后要求用户补充或给出失败说明 |
| 用户信息不足且无法安全推断 | Node 向用户询问最少必要信息；不填造资源、环境、SQL 或时间范围 |
| 模型企图提供或覆盖 `user_id`、`session_id`、`task_id`、确认凭据等服务端字段 | 拒绝候选调用并审计；可信字段仅从 Runtime/State 的受控来源注入 |
| 平台超时或失败 | 不把失败写成成功；Node 返回可理解的失败状态，按操作类型决定是否可重试 |

不得通过自动重试重复提交有副作用的请求。重试只针对尚未执行的模型候选参数；平台调用已发出后，依赖平台结果查询或幂等键判断状态。

### 5.3 高影响操作的后续接入

当 `execute_query`、`create_permission_ticket`、`submit_dag`、`trigger_dag`、`backfill_dag` 等工具后续接入时，Node 必须先完成现有 SQL 校验、权限检查、预览或人工确认。Harness 还须核对“当前阶段允许调用”及批准的关键参数快照；资源、环境、SQL、DAG 内容或回填区间变化时，原确认失效并重新确认。Schema 合法并不代表业务授权或用户同意。

## 6. 功能需求

### FR-01：统一工具契约与发布

- 为每个开放给模型的工具维护唯一、可版本化的契约：名称、说明、输入 Schema、服务端注入字段、阶段白名单、风险等级、超时与幂等策略。
- 输入 Schema 采用严格模式；未知字段默认拒绝。复杂参数（资源、日期范围等）要有嵌套结构和约束，不能只用无约束 `dict[str, Any]` 表示。
- 模型看到的 Schema、Harness 验证使用的 Schema 和适配器最终参数映射应来自同一契约，或在启动时做一致性检查。契约版本写入审计。
- 现有 `api_contracts.py` 可复用合适字段约束，但需核对服务方法签名与 HTTP 请求模型间的差异，尤其是由服务端注入的 `user_id` 等字段。

### FR-02：阶段限定的候选调用

- Node 显式传入本阶段允许的工具名列表和剩余调用预算；Harness 不接受模型自选的新列表。
- 首期每轮只接受一个候选调用；多调用、无调用和纯文本回复必须有确定处理结果，不得隐式执行。
- Node 可以基于已验证的工具结果进入下一阶段，但不能让模型凭输出文本跳过前置检查。

### FR-03：调用前验证与执行

- Harness 按顺序完成：解析候选调用、名称白名单校验、参数 Schema 校验、可信字段注入、阶段/业务策略校验，然后执行。任一步失败均不触达平台适配器。
- 模型提交的参数与最终执行参数分别保留，审计时对敏感信息做脱敏；实际执行参数中的用户身份始终来自服务端。
- 工具结果要有大小上限和安全摘要；原始结果按现有业务需要进入 State，但不能被当作下一轮的高优先级指令。

### FR-04：State、审计与可观察性

- State 增加当前阶段、候选调用、校验结果、已执行调用、失败原因和重试计数；保留现有 `tool_calls`、`audit_events` 的兼容语义。
- 审计至少能关联 `task_id`、`session_id`、`intent`、Node、工具名、契约版本、校验状态、拒绝原因、执行状态与耗时。不得记录 API 密钥和未脱敏的敏感值。
- 监控候选调用总数、名称拒绝率、Schema 拒绝率、纠错成功率、工具执行成功率、用户澄清率、单任务调用次数与耗时。

### FR-05：兼容与降级

- 用配置开关按工具或意图启用新模式；关闭时仍走现有节点固定调用流程。
- 模型服务不可用时，已支持的任务按现有规则路由/固定流程降级；不能在安全前置条件未完成时直接调用写操作。
- CLI、HTTP 返回格式和已有确认续跑接口保持兼容；内部新增校验失败状态可映射为现有响应结构。

## 7. 分期交付

| 阶段 | 交付内容 | 独立用户价值 |
| --- | --- | --- |
| P0：只读工具试点 | 统一契约、Harness 校验入口、阶段白名单、资产/元数据只读工具接入、审计、开关和降级 | 自然语言找表与查元数据可由模型选择合适工具与参数，非法调用被拦截 |
| P1：受控多步查询 | Node 按结果推进多个只读阶段，加入权限查询及 SQL 分析类工具，完善调用预算和澄清 | 用户的复合问题可在已有流程约束下完成多步查询 |
| P2：高影响操作 | 将 SQL 执行、权限工单及 DAG 操作接入候选调用机制，增加确认参数快照、幂等与恢复 | 用户可在明确预览和确认后完成操作，保持原有安全边界 |

## 8. 验收标准

### 8.1 P0 必须通过

1. 对所有已开放工具，模型生成合法名称和参数时，Harness 验证后仅执行一次，并能在审计中追溯 Node、契约版本和执行结果。
2. 对未知工具、非当前阶段工具、无效 JSON、缺参、错类型、越界值、额外字段和伪造 `user_id`，平台适配器调用次数均为 **0**；响应包含可定位的错误类别。
3. 相同用户问题在开关关闭时仍走现有流程；开关开启而模型不可用时可降级至现有可用流程。
4. Node 按预设阶段处理工具结果；模型输出不能直接修改 Graph 边、跳过权限检查或触发未开放的写操作。
5. 对至少包含资产发现、表/字段解释、指标查询、参数缺失及非法调用的评测集，对比现有固定流程记录任务完成率、正确工具率、参数一次通过率与延迟；上线阈值由基线评测确定，不能仅凭演示用例放行。

### 8.2 P1/P2 增量验收

- P1：多步调用不超过配置预算；每一步都有阶段白名单校验；缺少必要资源时先澄清。
- P2：未完成现有 SQL 校验、权限检查或用户确认时，高影响工具调用数为 0；确认后关键参数改变会重新确认；重复恢复不会重复提交同一操作。

## 9. 风险与待决问题

| 事项 | 处理方向 |
| --- | --- |
| 工具 Schema 与服务/HTTP 契约漂移 | 确定唯一契约来源，并在启动和测试中比较映射 |
| 模型为提高成功率猜测资源或环境 | 对关键字段设置明确证据要求；信息不足时澄清 |
| 工具结果中含提示注入文本 | 将返回值标记为不可信数据；Node 仅使用结构化事实推进流程 |
| 多步调用增加成本和时延 | 限制每阶段工具集合、调用次数及结果体积；与固定流程基线比较 |

待评审决定：P0 工具契约以独立 Pydantic 模型还是现有 `api_contracts.py` 扩展为主；只读工具一次校验失败后的纠错提示格式；按意图还是按工具灰度；P0 评测集的任务完成率与延迟门槛。

## 10. 关联实现位置

- `src/data_agent/routing.py`、`src/data_agent/llm.py`：当前可选 LLM 意图路由及降级。
- `src/data_agent/graph.py`、`src/data_agent/nodes.py`、`src/data_agent/state.py`：固定流程、阶段控制与任务状态。
- `src/data_agent/tooling.py`：现有工具注册、调用和审计；目标 Harness 的主要接入点。
- `src/data_agent/api_contracts.py`、`src/data_agent/services.py`：当前 HTTP 请求模型与平台服务签名。
